`pg_net` was enabled on 2026-11-02 so that the Meilisearch health/canary probe
(`search_probe_tick`, pg_cron, every 5 minutes) can reach Meilisearch from
inside Postgres. It is the only way to run that probe in the database, and the
database is the only place that can still report when the app itself is down —
which is the outage most worth detecting now that the storefront searches
Meilisearch directly and GroLabs sees nothing when search breaks.

Accepted knowingly, in exchange for that. This is the residual risk.

## What is actually exposed

Verified on 2026-11-02, not assumed:

- `net.http_get` and `net.http_post` are executable by **PUBLIC**, which
  includes `anon` and `authenticated`
  (`has_function_privilege('anon', …, 'EXECUTE')` → true).
- `net.http_request_queue` carries a `headers` column, so every probe's
  `Authorization: Bearer <search key>` sits there until the worker drains it.
  Low stakes for *this* credential specifically — the storefront search key is
  public by design and ships in page source (R-4) — but the mechanism stores
  whatever header any future caller sends.
- `net._http_response` carries `content` and `headers`: response bodies, kept
  until pg_net's own cleanup.

## Why it is medium and not high

The `net` schema is **not** exposed through PostgREST, so `anon` cannot call
`net.http_post` directly over the REST API today. The escalation path is
indirect: any SQL-injection, or any over-privileged `SECURITY INVOKER` function
in an exposed schema, previously bought an attacker a *read*. With pg_net
reachable it also buys an **outbound channel** — a way to send what they read
somewhere else, and a way to reach hosts the database can see and the internet
cannot. That is a meaningful change in what a single read-only bug is worth.

## Why it was not fixed on the spot

It was attempted and it does not work from a migration. Both of these ran
without error and changed nothing:

```sql
revoke execute on all functions in schema net from anon, authenticated;
revoke execute on all functions in schema net from public;
```

Schema `net` is owned by `supabase_admin`; migrations run as `postgres`, which
is **not** a member of it. Postgres silently no-ops a `REVOKE` issued by
someone who is neither the grantor nor the object owner — no error, no warning,
`has_function_privilege` unchanged. Worth knowing in its own right: a revoke
that "succeeded" here proves nothing, so any fix must be verified by querying
the privilege afterwards rather than by the statement not raising.

## How to close it

1. Revoke `EXECUTE` on `net.http_*` from `PUBLIC` as `supabase_admin` (Supabase
   support or the dashboard, since migrations cannot), then re-check
   `has_function_privilege('anon', 'net.http_post(...)', 'EXECUTE')` is false.
2. Keep `net` out of PostgREST's exposed schemas. It is out today; this is a
   thing to assert in a test, not to assume stays true.
3. Consider narrowing further: a `SECURITY DEFINER` wrapper that accepts only
   the configured Meilisearch host from `search_probe_config`, with direct
   `net.*` access removed, so the database can call exactly one origin.
4. Confirm `net._http_response` is being purged. Our probe stores only a status
   code in `backend_operation`, never the body, but pg_net keeps its own copy.

If closing step 1 proves impossible on this plan, the honest alternative is to
reverse the step-13 decision: drop `pg_net`, move the probe to a scheduled
route handler, and accept that it cannot report on its own host's outage.
