`/api/v1/events` decides whether to trust a caller by comparing the `Origin`
header against `instance.storefront_domains`. A browser will not let a page lie
about its own origin — but nothing else is a browser. From curl, `Origin` is a
header you type.

**Anyone who knows a merchant's `myshopify.com` domain can inject arbitrary
telemetry for that instance**: fabricated searches, clicks, conversions,
revenue. The domain is not a secret; it is in the storefront's URL.

Demonstrated incidentally on 2026-11-02 — every verification batch in Phase 4
and Phase 5 was accepted purely because curl claimed
`Origin: https://grolabs-dordvapo.myshopify.com`. The endpoint could not tell
the difference, and there is nothing in it that could.

## Why this got worse, rather than appearing

The check is unchanged, but what rests on it is not. Before direct search,
`query_log` was written by the proxy that had *actually performed the search* —
a reported event could be checked against something that really happened. In
direct mode the row is only what a client claimed. Combined with R-32 (abuse is
invisible to us because an attacker simply never reports itself), the position
is that search analytics are now both **forgeable** and **unverifiable**.

That is tolerable for a dashboard nobody acts on. It is not tolerable for
numbers shown to customers, used in the no-result → synonym recovery loop, or
relied on for commercial decisions — which is exactly what `metric_daily` and
the KPI catalog are for.

## Status — partially mitigated 2026-11-02

Shipped: `/api/v1/events` now requires `Authorization: Bearer <storefront search
key>` whenever the instance holds a live key, verified against `search_key`.
Instances without a key are unaffected, so legacy single-event callers keep
working. The CORS preflight advertises `Authorization`, without which every
batch would have failed at the OPTIONS — silently, since reporting is
fire-and-forget.

Verified: no bearer → 403, wrong bearer → 403, raw key without the `Bearer`
scheme → 403, correct bearer → 202, and an instance with no key → 202.

Severity drops high → medium. **It is not closed.** The credential ships in
storefront page source, so this raises the bar from "knows the shop's domain"
to "has read that shop's page source". It defeats blind and scripted forgery
against a guessed domain; it does not stop a determined attacker targeting a
specific merchant. Step 1 below is done; 2 and 3 remain.

## How to close it

1. Require a bearer credential on `/api/v1/events`, not just an origin. The
   storefront already holds a per-instance key in its theme settings, so the
   cheapest strict improvement is to accept that: it ties a report to someone
   holding the instance's credential rather than someone who knows its domain.
2. Better: a dedicated per-instance **report key**, separate from the search
   key, so revoking one does not break the other. The `search_key` table and
   its panel are the pattern to copy — this is the same shape of problem.
3. Either way the credential is public (it ships in page source), so this
   raises the bar rather than sealing it. Sealing it needs a signed, expiring
   token, which is the renewal machinery R-2 deliberately removed. Do not
   reintroduce it without re-reading that decision.
4. Keep the origin check. It is still a useful filter; it is just not an
   authenticator.

## What it is not

Not a confidentiality breach. The endpoint only accepts writes of analytics
events; it exposes nothing. The damage is integrity of our own measurements.
