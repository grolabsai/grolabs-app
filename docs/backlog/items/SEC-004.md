One key covers search *and* event submission (R-5) — Meilisearch's `/events`
accepts a search-scoped key. That is what retired the per-page token fetch, and
it is also what makes the key a write credential.

Verified on 2026-11-02 against the live project with the real storefront key:

| probe | result |
|---|---|
| `POST /events` | **201** |
| `POST /indexes/inst_16/documents` | 403 |
| `POST /indexes/inst_11/search` | 403 |
| `GET /keys` | 403 |

So containment is otherwise correct — the key cannot write the catalog, read
another tenant, or enumerate keys. But the key ships in storefront page source
by design, so **anyone can forge clicks and conversions into Meilisearch's
analytics**, which feed its relevance feedback. Ranking and Meilisearch-side
analytics are therefore attacker-influenceable.

The probe that proved this wrote one event named `integrity probe` into
instance 16's Meilisearch analytics. Meilisearch has no per-event delete, so it
is still there. It is the dev store, and it is the evidence.

## Why this is medium and not high

Nothing is exposed and nothing is destroyed; the catalog index is untouched.
The cost is skew in a feedback signal. It is also **inherent to the pattern**
rather than a mistake in our build — Algolia's Insights API has exactly the
same property with a public search key, so switching platform does not fix it.

## How to close it

1. Decide whether Meilisearch-side relevance feedback is actually used. If it
   is not, stop sending events there: we collect our own telemetry now
   (Phase 4/5), so the Meilisearch `/events` write may be redundant, and
   removing it closes this with no loss.
2. If it is used, treat its analytics as advisory and never as a source for
   customer-facing numbers — ours come from `query_log` / `analytics_event`,
   which have their own integrity problem tracked as SEC-003.
3. Watch for implausible event volume against the probe's own canary traffic.
   There is no per-key rate limit in Meilisearch to lean on (R-15).

Related: [`SEC-003.md`](SEC-003.md), which is the same failure on our side of
the wire, and R-5 / R-32 in the design doc.
