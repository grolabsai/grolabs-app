Event semantics trace

One shopper journey. Each node is one event: open it to see the state the decision reads, the branch the code takes, and what gets recorded. Nodes marked SELF decide nothing from history — they would record the same thing on a fresh browser.

This page is generated. Every row says where its claim comes from, because the three kinds are not equally trustworthy.

Where each claim comes from

  • MEASUREDProduced by executing the real code at build time — src/lib/analytics/intent.ts run over this journey. No intent id or type name is typed anywhere in the generator, and the build fails if a measured value does not reach the page.
  • VERIFIEDProduced by running the real SQL once against the live database and recorded with its date (2026-11-02) — session numbers from session_assignment's own window expression, counts from query_log and analytics_event. Recorded rather than re-run so the build needs no credentials.
  • AUTHOREDRead out of the source by a person. What state a decision reads, which branches exist, what the definitions say. This is the half that can drift, and it is marked on every row so you know which cells to distrust.

What the badges on each event mean

Every closed row carries the record itself: the table written, then the values, with the MEASURED ones — those produced by running the real code — keyed in their own colour. Open a node for how the decision was reached. The badges answer two separate questions. The first three are does history matter here? and say nothing about whether the event is right; the last two are the verdict.

  • READSWhat this event records depends on an earlier one. Step 12, add to cart, carries a query_uid only because the click at step 10 stored one 40 seconds earlier. Take the click away and the same add-to-cart records something different.
  • WRITESIt leaves something behind that a later event will read. Step 10 is the click that writes that attribution. An event can be both: step 7 reads the window and then joins it.
  • SELFNeither — it would record exactly the same thing on a brand-new browser. Step 11, the product view, takes the product id off the page it is on. Nothing before it changes the row. These are the events you can test one at a time; the READS ones can only be tested in sequence.
  • MATCHWhat we record is what the definitions say to record. The branch the code took is the branch the grammar names.
  • GAPIt is not. The event is recorded, but as something other than what it means — so anything built on it is confidently wrong rather than missing. Five are left; each says which finding it belongs to, and the card below says why we record them at all.

Why record an event we know is wrong?

A GAP is not a bug report, and it is not a reason to drop the event. In every one of the five, the write succeeded — nothing threw, nothing returned an error, the row is in the table and the funnel counts it. The event is true; what is wrong is a claim placed on it. Three different ways that happens:

The field is not there to writeAUTHORED
Step 19 — add to cart, logged in. The shopper has just signed in, so the theme can see who they are. Then the pixel fires the conversion, and the pixel runs in a sandboxed worker with no access to the theme's customer object. The row lands: conversion, Added to cart, cart_id set, account_id NULL. HTTP 202. The cart thread is right, the funnel is right, the conversion count is right.

Dropping that event to avoid the missing field would be strictly worse — you would lose a real add-to-cart. So we record it, and the gap is that the definition calls login “the merge point where anonymous history attaches to the human”, and this is the one row that proves who the human is while carrying nothing that identifies them. Ask “what are logged-in customers buying?” and you get nothing back — not an error. The honest reading is “we don't stamp accounts on purchases”. The reading you'd actually take is “logged-in customers don't buy”.
Every column is correct, the grain is notAUTHORED
Step 23 — the same person, on their phone. This is the purest case: there is nothing to fix in the row. user_id, intent, session_seq — each is exactly what the code should write, given that identity lives in one browser's localStorage. The event must be recorded; a purchase on the second device is real revenue.

The gap is one level up. Counted against “one user, one session, one intent”, this person is now two users, their session counter has restarted at 1, and goggles has a fourth intent although step 21 already opened that demand. Your user count, session count and intent count are each one too high, and no column anywhere disagrees with itself. This is why a gap is not a bug: nothing malfunctioned.
The rule that ran is not the rule namedAUTHORED
Step 20 — “snowboard wax”. It joins the right demand and gets a type, so the row is complete and plausible. But the type is narrowing where the definition says lateral, because the chain judged it against wax rather than ski wax.

The two labels prescribe different work: narrowing says add a facet, lateral says add a synonym for ski ↔ snowboard. A missing type would send nobody anywhere; a confident wrong one sends them to the wrong fix.

So the remedy is never “stop recording”. It is to record the thing that tells the two cases apart — a field, a different grain, or a rule that matches the definition. A row that is absent shows up as a zero and someone asks why. A row that is present and means something else is read as fact.

The state these decisions read

Everything in the “given what happened before” column lives in one of these five places. Four are in the shopper's browser, which is why clearing storage or switching device changes what gets recorded.

Browser idauthored
localStorage grolabs_search_session_id, mirrored to cookie grolabs_bid. Persistent per browser — despite the name it is not a session. Becomes user_id on every row.
Attributionauthored
localStorage grolabs_search_attribution: productId → {queryUid, indexUid, position, name, ts}. 7-day TTL, 100 entries LRU. Written by a click, read by every later conversion.
Dedup flagsauthored
sessionStorage for checkout (sorted cart-id hash); localStorage for order (orderId) — once per order, ever.
Cart tokenauthored
localStorage grolabs_cart_token, threads add → checkout → order as cart_id.
Intent windowauthored
The only server-side one: committed query_log rows for this (instance, user), last 10, within 30 minutes.

Event time now survives the pipeline — reported as an age, not a timestamp

Every timestamp above is the shopper's. It used not to reach the row at all: the storefront stamped no event time, event_inbox kept only received_at, and the drain omitted created_at — so it took the default, the moment the drain ran, collapsing every event in a drain window onto one instant and flattening the 30-minute gaps these session boundaries are built on. The storefront now reports how long ago each event happened and the receiver computes occurred_at = received_at − age_ms against our own clock. An age rather than a timestamp because both readings behind it come from the device's own clock, so a phone set to the wrong year still reports a correct age and the error cancels; an absolute client timestamp would have imported every broken clock on the internet into the KPI series. The drain is scheduled now, and walks each batch in event-time order rather than arrival order, because the retry queue can deliver an old event after a newer one. Rows written before this keep drain time and are not backfillable — the information was never sent.
